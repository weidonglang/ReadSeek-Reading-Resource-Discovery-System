# ReadSeek Evaluation Report

## 1. Evaluation Overview

This report evaluates ReadSeek from four aspects:

1. Retrieval effectiveness
2. RAG answer quality
3. Recommendation quality
4. API performance

The purpose is to verify whether hybrid retrieval, reranking, evidence-grounded RAG, and explainable recommendation make the system more than a CRUD-based library application.

The latest real local benchmark results are generated by `readseek-bench-rs` and stored under:

```text
docs/evaluation/generated/rust-suite/
```

## 2. Retrieval Evaluation

### 2.1 Dataset

- Book collection size: 373 demo books
- Query set size: 100 queries
- Query types:
  - exact title queries
  - author-work queries
  - Chinese and English topic queries
  - natural-language description queries
  - multi-condition queries
  - comparison queries
  - reading-path queries
  - metadata fallback queries

### 2.2 Compared Methods

- BM25
- Dense vector retrieval
- Hybrid retrieval
- Hybrid retrieval + reranker

### 2.3 Metrics

- Precision@5
- Recall@5
- MRR
- NDCG@10
- Average latency
- P95 latency

### 2.4 Result Summary

| Method | Success | Precision@5 | Recall@5 | MRR | NDCG@10 | Avg ms | P95 ms |
|---|---:|---:|---:|---:|---:|---:|---:|
| BM25 | 100/100 | 0.3080 | 0.1904 | 0.6440 | 0.3568 | 42.6 | 78.8 |
| Vector | 100/100 | 0.4940 | 0.2536 | 0.8884 | 0.5078 | 62.0 | 73.3 |
| Hybrid | 100/100 | 0.3460 | 0.2017 | 0.7043 | 0.3922 | 110.9 | 142.9 |
| Hybrid + Reranker | 100/100 | 0.5040 | 0.2630 | 0.9167 | 0.5035 | 266.2 | 316.9 |

### 2.5 Analysis

Hybrid + Reranker achieves the best Precision@5, Recall@5, and MRR in this benchmark. Vector retrieval has the highest NDCG@10 and lower latency than reranking, which makes it useful for semantic search when response time is more important.

Reranking improves top result quality, but adds latency. This tradeoff should be explained clearly in project defense: the system can choose between vector, hybrid, and hybrid + reranker depending on the query scenario and performance requirement.

Manual scoring columns are kept in `rag_evaluation_manual_scoring.csv` for later human review of relevance, completeness, citation validity, and hallucination risk.

### 3.4 Analysis

The RAG module can answer all test questions under the current benchmark setting and usually retrieves relevant supporting evidence. The main limitation is latency, which depends heavily on local Ollama model size and hardware performance.

This result should be described as local evidence-grounded RAG evaluation, not as a large-scale public RAG benchmark.

### 5.3 Analysis

Recommendation APIs are relatively fast in the local benchmark. Search APIs are slower because hybrid retrieval may involve Elasticsearch, vector search, BGE-M3 embedding, and reranking. This latency is acceptable for a local engineering demo but should be optimized for production use.

## 6. Failure Cases and Limitations

### 6.1 Retrieval Failure

Some vague queries may still return broad or weakly related resources when the catalog lacks enough matching metadata or when relevant resources are sparse.

### 6.2 RAG Failure

When retrieved evidence is insufficient, generated answers can become too general. The system should continue to emphasize limitation messages and citation-grounded answers.

### 6.3 Recommendation Failure

For cold-start users, recommendation quality depends heavily on popularity, category preferences, and initial user behavior. More real usage data is needed to improve personalization.

## 7. Conclusion

The evaluation shows that ReadSeek is more than a CRUD-based library system. Its core value lies in combining hybrid retrieval, reranking, evidence-grounded RAG, explainable recommendation, behavior analytics, and measurable offline evaluation.

The current results are suitable for undergraduate engineering demonstration and project defense. They should not be overstated as industrial-scale recommendation or public benchmark results.
